# ADR 0004 — Исполнитель изменений (worker): проект

Статус: **предложено, НЕ реализовано** · Дата: 2026-11-10 · Требует явного утверждения владельца (см. «Решения для владельца»)

## Контекст
После ADR 0002 подтверждённый план только фиксирует согласие (`executionAvailable: false`). Исполнитель — самая рискованная часть продукта: он меняет чужие серверы. Здесь зафиксированы границы, в которых его можно писать. Код, который подключается к серверам на запись, НЕ пишется до утверждения этого документа.

## Принципы (не обсуждаются)
1. **Исполняется только каталог** (`policy/catalog.py`). Произвольной команды нет ни в плане, ни в очереди, ни на сервере.
2. **Привилегии выдаёт владелец сервера вручную**, а не ServerMind. Пользователь `servermind` остаётся без общего sudo и без группы docker (она равна root).
3. **Перепроверка перед каждым шагом**, не только при подтверждении: план `approved`, не истёк, хеш пересчитан по содержимому и совпал с `approvals`, ключ хоста совпадает с закреплённым, сервер онлайн, политика пройдена заново на свежих данных.
4. **Остановка на первой ошибке.** Автоматического продолжения и «умного» самоисправления нет. Откат — только тот, что описан в каталоге, и показывается человеку.
5. **Существующие службы не трогаем.** Новые ресурсы создаются только в своём пространстве имён; конфликт (порт, имя проекта, существующий контейнер) = отказ, а не перезапись.
6. **Выключено по умолчанию:** глобальный `EXECUTION_ENABLED=false`, флаг организации и флаг сервера. Для запуска нужны все три.

## Предлагаемая архитектура
- **Очередь в PostgreSQL** (`jobs`, `job_steps`), один процесс-воркер, захват `FOR UPDATE SKIP LOCKED`, аренда с таймаутом, идемпотентный ключ `(plan_id, revision, step_index)`. Результаты шагов append-only (триггер, как у `audit_events`); вывод ограничен и очищен `redact()`.
- **Как получить root для фиксированных операций (вариант A, рекомендуется):** владелец один раз ставит на сервер корневой скрипт-обёртку `/usr/local/sbin/servermind-op` и запись sudoers, разрешающую пользователю `servermind` запускать ТОЛЬКО эту обёртку. Обёртка принимает имя операции из белого списка и параметры, заново валидирует их (те же регулярные выражения, что в каталоге) и выполняет заранее написанные команды. Её текст показывается владельцу в интерфейсе до установки и версионируется (хеш). Компрометация ServerMind даёт только операции каталога, не root-оболочку.
- **Вариант B (не рекомендуется):** отдельные строки sudoers под каждую команду без обёртки. Сложнее аудировать, проще допустить обход через аргументы.
- **Режим «репетиция» (dry-run)** обязателен как первая версия: исполнитель выполняет все проверки и печатает, что сделал бы, ничего не меняя. Реальное исполнение включается отдельным шагом после ревью.
- **Журнал:** каждый шаг пишет в аудит (кто подтвердил, хеш, шаг, результат, длительность). Интерфейс «Операции» показывает реальный журнал вместо ссылки на экран подтверждения.

## Операции и ограничения
| Операция | Предусловия (отказ при невыполнении) | Что НЕ делает |
|---|---|---|
| `service.restart` | служба в `managed_services` и существует; диск не критичен | не трогает зависимые службы, не меняет юнит-файлы |
| `docker.install` | Docker ещё не установлен (если есть — отказ, не переустановка); Ubuntu 24.04; официальный репозиторий | не добавляет пользователя в группу docker |
| `app.deploy_compose` | Docker есть; порт свободен; имя проекта в нашем пространстве `servermind-<id>`; образ из разрешённых реестров, по digest | не монтирует docker.sock/хост, не privileged, не меняет чужие контейнеры |
| `http.healthcheck` | только `127.0.0.1` | не ходит во внешнюю сеть |
| `domain.configure_https` | остаётся выключенной (нужен DNS preflight и отдельное ревью) | — |

## Модель угроз (кратко, требует доработки до реализации)
- **Утечка БД + мастер-ключа** = доступ ко всем подключённым серверам в рамках каталога. Смягчение: ключ вне БД, обёртка с белым списком, журнал, возможность отозвать ключ сервиса на сервере.
- **Подмена плана** → хеш и пересчёт перед каждым шагом (уже есть в ADR 0002).
- **Инъекция через вывод сервера** → вывод очищается, ограничивается и не попадает в команды.
- **Подмена сервера (MITM)** → закреплённый ключ хоста; смена блокирует исполнение.
- **Зависшая операция/повторный запуск** → таймауты, аренда, идемпотентные ключи, один активный план на сервер.
- **Ошибка в самой обёртке** — главный остаточный риск: её нужно ревьюить отдельно и тестировать на одноразовой ВМ, не на рабочем сервере.

## Решения для владельца
1. Вариант A (обёртка + sudoers) или B?
2. Первая версия — только «репетиция» (рекомендуется), или сразу реальное исполнение?
3. Разрешено ли тестировать реальное исполнение на **одноразовой** ВМ (не на сервере с ServerMind и не на рабочих)? Тестирование на вашем боевом сервере я не предлагаю.
4. Какие операции входят в первую версию? Предложение: `service.restart` и `http.healthcheck`; `docker.install` и `app.deploy_compose` — после них.

## Не проверено
Ничего из описанного не реализовано и не запускалось. Работа обёртки с реальным sudo, поведение при обрыве SSH в середине шага и нагрузка очереди — предмет будущих проверок.
