# ADR 0002 — AI как недоверенный планировщик: политика, планы, подтверждения

Статус: принято (Фаза 3) · Дата: 2026-11-10

## Решение

1. **Модель не имеет прав.** Ей доступны только (а) инструменты чтения `server.facts`, `server.metrics`, `service.status` — они читают *уже сохранённые* проверенные измерения, на сервер не ходят; (б) `propose_plan`, который **ничего не исполняет**: предложение проходит policy engine и сохраняется как план `waiting_approval`.
2. **Каталог операций** (`app/modules/policy/catalog.py`) — единственный список возможных шагов: `docker.install`, `app.deploy_compose` (только шаблон `web-app`, образ из разрешённых реестров, без privileged/host-mount/docker.sock), `service.restart` (только `managed_services` ∩ службы сервера), `http.healthcheck` (только `127.0.0.1`), `domain.configure_https` (выключено: manual only). Параметры — pydantic с `extra=forbid`. Риск ≤ R3, R4/R5 запрещены.
3. **Policy engine** проверяет: роль (owner/operator), онлайн-статус сервера, наличие данных, службы, диск < 90% для тяжёлых операций, Docker перед деплоем, один деплой, дубликаты, размер плана. Все причины отказа возвращаются модели и пишутся в аудит.
4. **Хеш плана** — SHA-256 канонического JSON `{plan_id, server_id, revision, expires_at, steps[{tool, params, risk}]}` (ключи отсортированы, без пробелов, включены только активные шаги). Тот же алгоритм в браузере; контракт закреплён общими векторами в `tests/test_plan_hash.py` и `lib/plan.test.ts`.
5. **Подтверждение** (`POST /action-plans/{id}/approve`): owner/operator, статус `waiting_approval`, срок не истёк, ревизия и хеш совпадают с сохранёнными **и** с пересчитанными по реальному содержимому (подмена данных в БД обнаруживается). Запись `approvals` привязана к (plan, revision, hash, actor), append-only триггером БД. Любое изменение плана → новая ревизия и хеш → прежнее подтверждение недействительно.
6. **Исполнения в этой фазе нет.** Подтверждение лишь фиксирует согласие (`executionAvailable: false`). Worker, который перепроверит политику/срок/хеш перед каждым шагом, — Фаза 4.
7. **Провайдеры:** тонкие адаптеры к официальным API (OpenAI, Anthropic, DeepSeek), URL — константы, ключ только в заголовке, редиректы выключены. Имя модели задаёт пользователь (списки моделей меняются; значений «из головы» нет). BYOK-ключ шифруется AEAD с привязкой к организации; проверка ключа — запросом списка моделей (не `chat`).
8. **Контекст модели:** минимальный (без IP/порта/имени SSH-пользователя), очищенный от секретов, обрезанный, в явной разметке `<untrusted_server_data>`; история ограничена по числу сообщений и символов.

## Что это даёт и чего НЕ даёт
Даже полностью скомпрометированная инъекцией модель не может изменить сервер: нет пути исполнения, неизвестные инструменты отклоняются, план проходит политику и требует человека. Это **не** защищает от вводящих в заблуждение, но допустимых по политике планов — поэтому подтверждение показывает точные параметры, риск, простой и хеш.

## Не проверено
- Форматы запросов к провайдерам сверены с документацией для Anthropic и DeepSeek; формат OpenAI — по памяти (страница документации вернула 403). **Ни один адаптер не вызывался живым ключом.**
- Поведение реальных моделей при инъекциях (тесты используют сценарные заглушки, моделирующие «послушную» модель).
- Режим Credits (ledger, резервы) — Фаза 5; сейчас `PUT /billing/mode credits` → 409.
