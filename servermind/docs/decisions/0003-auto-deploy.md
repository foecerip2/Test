# ADR 0003 — Автоустановка и автообновление на VPS

Статус: принято (Фаза 4, часть «развёртывание») · Дата: 2026-11-10

## Задача
Установить проект на VPS одной командой и обновлять его автоматически, когда в GitHub появляется новая версия.

## Рассмотренные варианты
| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Pull: VPS сам опрашивает реестр (выбран)** | В GitHub нет ключа к серверу (нет входящего SSH, нет секретов продакшена в Actions); работает за NAT; откат и бэкап — на самом сервере | Задержка до минуты; нужен доступ VPS к GHCR |
| B. Push: Actions заходит на VPS по SSH | Мгновенно | Приватный SSH-ключ к серверу в секретах GitHub; нужен открытый SSH; компрометация репозитория = доступ к серверу |
| C. Webhook на VPS | Быстро | Публичный endpoint с правами деплоя — новая поверхность атаки |
| D. Watchtower и аналоги | Готово | Нет миграций/бэкапа/отката; доступ к docker.sock у стороннего контейнера |

## Решение
1. **CI собирает образы** (не VPS; MD §0.1) и публикует в GHCR: `servermind-web:sha-…`, затем `servermind-api:sha-…`. Digest веб-образа записывается в `release.json` внутри API-образа — релиз **атомарен**: единственный «переключатель» — тег `stable` у API-образа.
2. **Пакет развёртывания едет в образе** (`/app/deploy`: compose, Caddyfile, `update.sh`, юниты systemd). Установщик и обновлятор достают его из образа → конфигурация всегда соответствует версии кода, отдельного канала доставки нет.
3. **`stable` двигается только после тестов** (job `promote`, окружение `production`). В настройках GitHub можно включить обязательное одобрение — тогда обновление VPS идёт только после вашего «Approve».
4. **Обновлятор** (`systemd timer`, раз в минуту; `flock`): новый digest → бэкап БД (должен читаться `pg_restore -l`) → миграции (образы ещё не переключены) → запуск **по digest** → smoke-тесты (API `/readyz`, web, Caddy) → успех **или** откат на прежние образы/конфиг. Сломанный digest запоминается и не повторяется, пока не выйдет новый. Сеть/реестр недоступны — не ошибка, повтор позже. Пауза: `auto-update.disabled`, обслуживание: `maintenance.lock`.
5. **Установщик** (`install.sh`): идемпотентный, `--dry-run`, проверки ОС/RAM/диска/портов; **чужие службы не останавливает** (занятый порт — отказ с вариантами); Docker ставит только если его нет; секреты генерирует локально и не перегенерирует при повторе; токен GHCR — только из файла.

## Последствия и риски (честно)
- **Кто может писать в `main` (и одобрять `production`) — тот может выкатить код на VPS.** Нужна защита ветки и, желательно, обязательное одобрение окружения.
- Обновлятор работает от root и имеет доступ к Docker: это неизбежно для управления контейнерами. Он скачивает только образы из настроенного репозитория по digest.
- **Откат образов не откатывает схему БД.** Миграции должны быть обратно совместимыми (expand → contract). При сбое миграции схема не меняется (транзакционный DDL PostgreSQL). Бэкап перед каждой миграцией позволяет ручное восстановление.
- Бэкапы лежат на том же диске: копирование за пределы сервера нужно настроить отдельно (MD §0.1).
- Потеря `/opt/servermind/env/api.env` (мастер-ключ) = потеря зашифрованных данных.
- Self-update `update.sh` вступает в силу со следующего запуска; юниты systemd автоматически не обновляются.

## Что НЕ проверено (на 2026-11-10)
Docker-демона и VPS в среде разработки не было, поэтому **ни разу не выполнялось**: сборка образов, `docker compose up`, реальный HTTPS через Caddy, реальные pull из GHCR, работа systemd-таймера, установка Docker через apt. Проверено: логика `update.sh`/`install.sh` на поддельном docker (103 теста + мутационная проверка), `shellcheck`, `actionlint`, `systemd-analyze verify`, `docker compose config`, запуск веб-приложения в layout runtime-образа. Первая настоящая проверка Dockerfile — job `images` в CI.
