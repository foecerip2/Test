# Отчёт о производительности (Фаза 5)

Здесь только то, что **реально измерено**. Всё остальное явно помечено «не измерялось». Цифры с разного железа не смешиваются.

## 1. Реальный VPS: простой после установки (измерил владелец)
Хост: KVM, **1 vCPU, 1967 МБ RAM, 19 ГБ диска**, Ubuntu 24.04, ядро 6.8; swap 2 ГБ; установка `--low-memory` (лимиты контейнеров: PostgreSQL 320m, API 256m, web 224m, Caddy 48m), релиз `c8e3106`. Снято командами `free -m`, `swapon --show`, `docker stats --no-stream` через ~4 минуты после запуска, **без пользовательской нагрузки**.

| Показатель | Значение |
|---|---|
| RAM всего / занято / доступно | 1967 / 583 / 1384 МБ |
| Swap использован | 268 КБ из 2 ГБ |
| caddy | 14,2 МБ из 48 МБ лимита (29%) |
| web (Next) | 44,0 МБ из 224 МБ (20%) |
| api (FastAPI) | 74,4 МБ из 256 МБ (29%) |
| postgres | 23,1 МБ из 320 МБ (7%) |
| Состояние | все 4 контейнера `healthy`/`Up`, HTTPS отвечает `HTTP/2 307` без ошибки сертификата |

Вывод (только про простой): контейнеры занимают ≈ 155 МБ при суммарном лимите 848 МБ — запас большой. **Под нагрузкой и при росте БД картина другая, она не измерялась.**

## 2. Песочница разработки: профиль API (НЕ целевой VPS)
Машина: 4 vCPU, 16 ГБ RAM; API (uvicorn, 1 процесс, фоновый воркер включён) + PostgreSQL 16 на том же хосте, клиент `scripts/loadprofile.py` там же. Только `/healthz` (процесс) и `/readyz` (процесс + запрос к БД); без входа и без AI.

| Эндпоинт | Клиентов | Запросов | RPS | p50 | p95 | p99 | Ошибок |
|---|---|---|---|---|---|---|---|
| /healthz | 20 | 400 | 911 | 20,8 мс | 24,7 мс | 29,5 мс | 0 |
| /readyz | 20 | 400 | 422 | 45,6 мс | 71,5 мс | 82,2 мс | 0 |
| /healthz | 50 | 1000 | 1064 | 45,7 мс | 52,4 мс | 54,3 мс | 0 |
| /readyz | 50 | 1000 | 463 | 105,0 мс | 126,1 мс | 134,5 мс | 0 |

RSS процесса API в конце прогона ≈ 116 МБ. Эти числа **нельзя переносить на 1–2 vCPU VPS**: повторите `python3 scripts/loadprofile.py --base http://127.0.0.1:8000` на нём и снимите рядом `docker stats`.

## 3. Режимы из плана Фазы 5
| Режим | Статус |
|---|---|
| 1 vCPU / 4 ГБ | **не измерялся** (есть только 1 vCPU / 1,9 ГБ, см. п. 1) |
| 2 vCPU / 4 ГБ | **не измерялся** |
| VPS с заполненным на 70% диском | **не измерялся**; политика блокировки тяжёлых операций при диске ≥ 90% проверена автотестами, не на железе |
| Пиковая нагрузка, длительный прогон, утечки памяти | **не измерялись** |
| Перезагрузка VPS (контейнеры и таймер поднимаются сами) | **реальная перезагрузка не выполнялась.** Есть `bootstrap/post-reboot-check.sh` (проверен 13 тестами на подставных командах); `restart: unless-stopped` и systemd-таймер настроены. Выполните на VPS и занесите результат |
| Восстановление из бэкапа (restore drill) | `bootstrap/restore-drill.sh` **выполнен в песочнице** на схеме 0008 (дамп → восстановление во временную БД → проверки → удаление; повреждённый дамп распознан). **На реальном VPS не выполнялся** |

## 4. Как дополнить отчёт
1. На целевом VPS: `python3 scripts/loadprofile.py --base http://127.0.0.1:8000 --clients 20 --requests 400` (порт API внутри сети Docker не публикуется — запускайте через `docker compose exec api python3 …` или временно через Caddy-адрес `https://<домен>` для `/healthz`).
2. Параллельно: `docker stats --no-stream` раз в 5 секунд и `free -m`, `dmesg | grep -i oom` после прогона.
3. Для reboot-проверки: `reboot`, затем `docker compose -p servermind … ps` и `systemctl status servermind-update.timer`.
4. Занесите числа сюда с датой, конфигурацией хоста и версией релиза.
