- ✅ FastAPI + SQLAlchemy 2 + Alembic; миграция 0001 (up/down/up и `alembic check` без расхождений); триггер append-only для `audit_events`
- ✅ Вход: argon2id, cookie-сессии (HttpOnly, SameSite=Lax; токен в БД только SHA-256), CSRF-заголовок, idle/absolute-таймауты, ротация сессии, ограничение попыток входа, TOTP 2FA (обязателен owner/operator; код одноразовый — replay отклоняется; секрет шифруется AEAD)
- ✅ Tenant-изоляция: `organization_id` только из сессии, чужой ресурс = 404 (IDOR-тесты); роли owner/operator/viewer
- ✅ Политика адресов (SSRF): приватные/loopback/link-local/metadata/CGNAT/reserved, проверка всех DNS-ответов, подключение по проверенному IP, порты <1024 кроме 22, root запрещён
- ✅ SSH (только чтение): закреплённый ключ хоста, подмена → блок до выполнения команд; вход по ключу; 7 фиксированных команд; вывод ограничен и очищается от секретов; недостающие данные = `null`
- ✅ Приватный ключ сервиса на организацию: AEAD-шифрование (AES-256-GCM, привязка к организации), master key вне БД
- ✅ API: `/auth/*`, `/me`, `/servers` (+probe, public-key, verify, metrics, services), `/healthz`, `/readyz`; аудит событий
- ✅ Web подключён к API: CSRF, экран обязательной настройки 2FA
- ✅ Проверки: pytest **100 passed** (реальная PostgreSQL + настоящий SSH-протокол на тестовом сервере asyncssh), ruff чисто, сквозной Playwright на реальном стеке (браузер → Next → FastAPI → PostgreSQL) **3/3**
- ⬜ **Gate «VPS подключается по SSH» НЕ выполнен**: песочница не имеет исходящего SSH. Проверка на реальном сервере — шаги в README («Проверка на реальном VPS»)
- 🟡 Ограничения: `client_ip` без доверенного proxy (Фаза 4, Caddy); периодического опроса нет (`intervalSec: 0`, точки появляются при ручной проверке); сессии/смена пароля/сброс 2FA не имеют UI и эндпоинтов (`/me/sessions`, `/me/policy` и др. — Фаза 5); веб-клиент не умеет добавлять приватные адреса (намеренно); логи служб (`/services/{unit}/logs`) не реализованы; не проверены: нагрузка, одновременные сессии, перезапуск БД
- ⬜ Пароли: смена/сброс, политика сложности (сейчас ≥12 символов только в CLI)

## Фаза 4 — развёртывание и автообновление (ADR 0003)
Выбрана по запросу владельца часть «автоустановщик + автообновление из GitHub». **Исполнитель изменений на целевых серверах (worker, очередь, `docker.install`/деплой шаблонов) НЕ реализован** — это остаётся в Фазе 4 и требует отдельного разрешения.
- ✅ Dockerfile api/web (непривилегированные пользователи, образы собирает CI), production compose (лимиты RAM по бюджету MD, внутренняя сеть БД, только порты Caddy наружу, без privileged/host/docker.sock), Caddyfile (HTTPS по домену или HTTP для теста)
- ✅ `install.sh`: идемпотентный, `--dry-run`, проверки ОС/RAM/диска/портов, чужие службы не трогает, секреты генерируются локально (600) и не перегенерируются, токен GHCR только из файла
- ✅ `update.sh` + systemd timer: новый digest `stable` → бэкап БД (читаемый) → миграции → запуск по digest → smoke → откат; сломанный релиз не повторяется; пауза/обслуживание; блокировка параллельного запуска; проверка диска
- ✅ CI/CD (`.github/workflows/servermind.yml`): тесты api/web/bootstrap, сборка и smoke образов, публикация в GHCR, тег `stable` через окружение `production` (опциональное одобрение)
- ✅ Проверено: тесты bootstrap **103 passed** (52 обновлятор + 51 установщик, на поддельном docker), мутационная проверка update.sh **12 из 12**, `shellcheck`/`actionlint`/`yamllint` чисто, `systemd-analyze verify`, `docker compose config`, веб запускается в layout runtime-образа, `api.env` принимается реальным конфигом API
- ⬜ **Не выполнялось ни разу:** сборка образов, `docker compose up`, HTTPS/ACME, pull из GHCR, systemd-таймер на живой системе, установка Docker через apt. Первая реальная проверка Dockerfile — job `images` в CI; затем — установка на тестовый VPS
- 🟡 Ограничения: версии GitHub Actions заданы мажорными тегами (не SHA, не сверены); образы postgres/caddy — плавающие теги; `cap_drop` у postgres не задан; бэкапы только локально; уведомления о сбое обновления только в журнале и `last-update.json`; `client_ip` за Caddy/Next — адрес контейнера (лимит входа по IP ненадёжен, по email работает)
- ✅ Облегчённый режим `--low-memory` (+ опциональный `--swap-size`) для VPS ≈2 ГБ: лимиты через `SM_MEM_*` в `compose/.env`; проверено на поддельном docker (лимиты записываются, swap только по флагу, dry-run ничего не меняет). **Реальная работа на 2 ГБ не измерялась**
- ✅ Исполнитель, режим «репетиция» ([ADR 0004](docs/decisions/0004-executor-worker.md)): очередь `jobs`/`job_steps` (PostgreSQL, SKIP LOCKED, аренда), перепроверка плана перед КАЖДЫМ шагом (статус, подтверждение, хеш по содержимому, срок, права подтвердившего, сервер онлайн, политика на свежих данных), идемпотентность, append-only журнал, изоляция организаций; API `POST /action-plans/{id}/rehearse`, `GET /jobs`, `GET /jobs/{id}`. pytest 220. **На серверы ничего не отправляется** (тест подменяет asyncssh и падает при любой попытке подключения)
- ⬜ Реальное исполнение: обёртка `servermind-op` + sudoers (вариант A), тесты на одноразовой ВМ (её нет — нужна до включения), `docker.install` и `app.deploy_compose`, UI «Операции» на реальных данных
- ⬜ Worker, очередь заданий, исполнение `docker.install` / `app.deploy_compose` на целевых серверах — отдельное разрешение владельца и security review

- Фикстуры в памяти страницы (сброс при перезагрузке); дубли запросов между компонентами; хеш плана считается в браузере — нужен общий формат с сервером (предложение: RFC 8785); `next start` с `standalone` даёт предупреждение; Playwright использует предустановленный Chromium через `executablePath`
