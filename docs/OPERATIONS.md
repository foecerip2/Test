# OPERATIONS — установка на сервер и обновления

## Как это работает (просто)
1. Разработчик (Claude) готовит изменения в ветке и открывает pull request.
2. **Вы разрешаете слияние в чате** — это и есть ваше одобрение. Без вашего слова в `main` ничего не попадает.
3. После слияния GitHub сам гоняет тесты.
4. Сервер каждые ~3 минуты смотрит на ветку `main`. Как только появился новый коммит **с зелёными тестами**, он сам собирает сайт и запускает. Если новая версия не поднялась — сам возвращает прежнюю.

Кнопок на GitHub нажимать не нужно. Токены, ключи и секреты не настраиваются: сервер сам забирает публичный код, GitHub к серверу не подключается.

> Всё, что попало в `main` и прошло тесты, окажется на сайте. Поэтому: write-доступ к репозиторию держите только у себя, а по желанию включите защиту ветки `main` (Settings → Branches → Add rule → «Require a pull request before merging»).

## Установка на сервер (один раз)
Зайдите на сервер под root (консоль провайдера или SSH) и вставьте одну команду:

```bash
curl -fsSL https://raw.githubusercontent.com/foecerip2/Test/main/infra/deploy/install.sh | bash -s -- --repo foecerip2/Test --domain ai.vaylonet.ru
```

Пока изменения не слиты в `main`, замените `main` в ссылке на `ccr-daf26eef-2e6wi4` и добавьте `--ref ccr-daf26eef-2e6wi4`.
Но следить сервер всегда будет за `main`: до слияния PR нечего выкатывать.

Скрипт: проверяет, что `ai.vaylonet.ru` указывает на этот сервер и порты 80/443 свободны (если заняты — ничего не меняет и останавливается); ставит Docker, firewall (22/80/443), fail2ban, автообновления безопасности, swap 2 ГБ; ставит службу обновления и `lh-config`; генерирует секреты базы и API в `/opt/leadhunter/.env` (существующие значения не затирает). Вход на сайт — по коду из письма (ADR-015), временного пароля больше нет; шлюз basic-auth по умолчанию выключен.

Флаги: `--harden-ssh` (отключить вход по паролю; только если у root уже есть SSH-ключ и на сервере есть SSH), `--no-first-run` (не проверять обновления сразу), `--new-password` (устарел и ничего не делает; шлюз basic-auth включается командой `lh-config gate on`).

Установщик можно запускать повторно: он идемпотентен, настройки и секреты сохраняются, обновляет только службу и конфигурацию.

**Если сервер был установлен раньше (до ADR-015)**: в `.env` уже задан `BASIC_HASH`, поэтому шлюз остаётся включённым. Когда почта настроена и вход работает, выполните `lh-config gate off`.

**Файрвол.** Все уже слушающие внешние порты (SSH, консоль провайдера) остаются открытыми, дополнительно открываются 80 и 443. Если на сервере нет SSH (вход через консоль провайдера), fail2ban и отключение пароля пропускаются.

После установки: **смените пароль root** (он был отправлен в чат) — команда `passwd`.

## Управление на сервере
```bash
lh-update --rollback              # откат на предыдущую версию (откатанный коммит заново не выкатывается)
touch /opt/leadhunter/.paused     # приостановить автообновление;  rm /opt/leadhunter/.paused — возобновить
journalctl -u lh-update -n 50     # что делала служба обновления
systemctl list-timers lh-update.timer
lh-config show                    # настройки (секреты замаскированы)
lh-config gate on|off             # необязательный пароль-шлюз basic-auth перед сайтом
docker compose --env-file /opt/leadhunter/.env -f /opt/leadhunter/docker-compose.prod.yml ps
```

## Откат
- Автоматически: если новая версия не прошла проверку здоровья, сервер возвращает прежнюю и больше её не пробует.
- Вручную: `lh-update --rollback`. Или попросите разработчика слить в `main` исправление/возврат (`git revert`).

## Ограничения
- Установщик и служба проверены на подставных `git`/`docker`/GitHub API; на реальном сервере ещё не запускались, как и сборка Docker-образа (в среде разработки нет Docker-демона) — первая настоящая сборка пройдёт в CI.
- Сторонние GitHub Actions указаны по тегам; перед продакшном закрепить по SHA (ADR-007).
- Образ api, DATABASE_URL (драйвер `postgresql+psycopg`) и команда `python -m app.cli send-test-mail` согласованы с apps/api только по договорённости; на реальном сервере не проверялись.
- Сборка идёт на самом сервере. На маленьком сервере (например 1 ядро, 2 ГБ RAM) установщик добавляет swap 3 ГБ, а сборка занимает 5–10 минут; при нехватке памяти сборка может не пройти — тогда версия помечается неудачной и остаётся прежняя.
- Публичный GitHub API без токена ограничен 60 запросами в час с одного IP; служба делает 2 запроса при каждой проверке только когда нужно, поэтому укладывается в лимит.

## Состав стека и память (сервер 1 ядро, ~1.9 ГБ RAM)
Потолки `mem_limit`: web 384 МБ + api 256 МБ + postgres 256 МБ + caddy 96 МБ = 992 МБ. Остаётся ~900 МБ на ОС, Docker, службу обновления и кэш файлов. Postgres настроен скромно (`shared_buffers=64MB`, `max_connections=30`). Сборка образов (node до ~1 ГБ) идёт на самом сервере поверх работающего стека: поэтому нужен swap (установщик ставит 3 ГБ), образы web и api собираются последовательно. Если во время сборки сервер упирается в память, сборка может упасть — версия помечается неудачной, прежняя продолжает работать. Если на практике RAM не хватит — переносить сборку в CI/реестр образов (отдельное решение).

## Миграции базы и откат
Контейнер `api` при старте сам выполняет `alembic upgrade head`. Откат (автоматический или `lh-update --rollback`) возвращает **образы** web и api, но **не схему БД**. Поэтому миграции должны быть обратно совместимыми с предыдущей версией кода: сначала добавляем (колонки nullable/с default, новые таблицы), и только в следующем релизе удаляем/переименовываем то, чем старый код уже не пользуется. Если здоровье api не пройдено после миграции, сервер вернёт старый образ api на уже мигрированную схему; поэтому разрушающие миграции без двухшаговой схемы недопустимы. Перед рискованными миграциями делайте дамп: `docker compose --env-file /opt/leadhunter/.env -f /opt/leadhunter/docker-compose.prod.yml exec -T db pg_dump -U leadhunter leadhunter > backup.sql` (автоматических бэкапов пока нет, ADR-012).

## Регистрация и одобрение владельцем
Регистрация открыта для любого e-mail: человек вводит адрес и получает код. Пользователи, кроме `OWNER_EMAIL`, после входа **ждут одобрения владельца в приложении** и до этого ничего не видят. Владелец (`OWNER_EMAIL`) одобряется автоматически. Пока SMTP не настроен, запрос кода отвечает `503 MAIL_UNAVAILABLE` — это задумано (безопасный отказ: коды никуда не пишутся в логи и не показываются).

## Почта для кодов подтверждения (Рег.ру)
Идея: ящик `noreply@vaylonet.ru` на хостинге «Хост-0» Рег.ру; сервер шлёт через него коды входа. Пароль ящика вводится **только на сервере** командой `lh-config smtp` — не присылайте его в чат.

1. **Создайте ящик.** Войдите в панель хостинга (ISPmanager) → «Почта» → «Создать ящик» (названия пунктов могут немного отличаться в вашей версии панели) → домен `vaylonet.ru`, имя `noreply`, придумайте пароль (без пробелов по краям, без кавычки в начале и без « #»; лучше буквы, цифры и `-_.!`) → сохраните.
2. **Узнайте параметры SMTP.** Точный адрес сервера и порты берите в справке Рег.ру по почте хостинга или в карточке ящика/домена в панели — здесь я их не выдумываю. Обычно для хостинга: сервер входящей/исходящей почты — имя хостинга/почтовый сервер Рег.ру, порт `465` (шифрование `ssl`) или `587` (`starttls`), логин — **полный адрес** `noreply@vaylonet.ru`, пароль — от ящика. Если сомневаетесь, откройте справку Рег.ру «Настройка почтовых программ» для вашего тарифа и перепишите оттуда сервер/порт.
3. **Введите параметры на сервере** (консоль провайдера или SSH, под root):
   ```bash
   lh-config smtp
   ```
   Команда спросит: шифрование (`ssl` или `starttls`), сервер, порт, логин, пароль (ввод скрыт, повторить дважды), адрес «от кого» (`noreply@vaylonet.ru`). Значения проверяются, пишутся в `/opt/leadhunter/.env` (права 0600, атомарно), пароль не печатается. Затем она предложит пересоздать api и отправить тестовое письмо.
4. **Проверьте письмо:** `lh-config smtp-test you@example.com`. Письмо должно прийти в течение минуты.
5. **Укажите владельца:** `lh-config owner you@example.com` — этот адрес одобряется автоматически и управляет одобрением остальных. Проверить итог: `lh-config show`.

**SPF / DKIM для `vaylonet.ru`.** Без них письма часто попадают в «Спам». В «Управление DNS» домена на Рег.ру проверьте: (а) есть TXT-запись SPF (`v=spf1 …`), в которой учтена почта хостинга (какой именно `include:` нужен — смотрите в справке Рег.ру по почте хостинга, не придумывайте); запись должна быть одна; (б) DKIM: в ISPmanager → «Почта» (раздел домена/ящика) включите подпись DKIM, если пункт есть; панель покажет TXT-запись, которую нужно добавить в «Управление DNS». Если пунктов нет — уточните в поддержке Рег.ру, поддерживается ли DKIM на вашем тарифе. Дополнительно желательна запись DMARC (`_dmarc`), но это уже по желанию.

**Если письма попадают в «Спам»:** проверьте SPF/DKIM (выше); пометьте письмо «не спам» в своём ящике; не используйте в адресе «от кого» чужой домен (только `@vaylonet.ru`); смотрите логи: `docker compose --env-file /opt/leadhunter/.env -f /opt/leadhunter/docker-compose.prod.yml logs --tail 50 api`.

**Лимиты отправки.** У хостинга Рег.ру есть ограничения на число исходящих писем в час/сутки; точные цифры зависят от тарифа — **уточните в справке или у поддержки Рег.ру**. Для кодов входа небольшого числа пользователей этого достаточно; при росте нужен отдельный почтовый сервис.
