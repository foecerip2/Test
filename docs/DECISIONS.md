# DECISIONS (ADR)

Формат: контекст → решение → последствия. Статус `proposed` = ждёт подтверждения владельца.

## ADR-001 · UI без Tailwind/shadcn · proposed
Контекст: ТЗ §4 указывает Tailwind + shadcn/ui; CLAUDE_IMPLEMENTATION и задача требуют не generic-шаблон.
Решение: CSS-переменные из DESIGN_SYSTEM + собственные компоненты (CSS Modules), headless-примитивы только для a11y (диалог/меню) при необходимости.
Последствия: больше ручной работы, точнее совпадение с прототипом, меньше зависимостей и бандл.

## ADR-002 · Маршруты и API · proposed
8 маршрутов `/overview /discovery /companies /approvals /inbox /pipeline /analytics /settings` + `/login`, `/companies/[id]`. API `/api/v1` по ТЗ §7 + `/analytics/summary`. Имена таблиц по ТЗ §6.

## ADR-003 · Единый бэкенд-образ · proposed
`apps/api` содержит пакет `leadhunter`; `workers/*` импортируют его; один Docker-образ запускается как `api` / `worker` / `beat`. Экономит диск и время CI на 40 ГБ.

## ADR-004 · Caddy вместо Nginx · proposed
Авто-HTTPS (Let's Encrypt), простая конфигурация, малый расход RAM. ТЗ §3 допускает оба.

## ADR-005 · Celery + Redis · accepted (ТЗ)
concurrency=2, recycle по памяти, состояние в PostgreSQL. Пересмотр только по результатам замера.

## ADR-006 · Одна origin, cookie-сессии · proposed
Caddy проксирует `/api`. Сессия `HttpOnly; Secure; SameSite=Lax`, CSRF double-submit, короткий TTL, rate limit, Argon2id, TOTP (опционально, Фаза 2).

## ADR-007 · Деплой с ручным утверждением · superseded by ADR-014
Исходная идея (GitHub Environment + required reviewer + SSH-деплой) заменена pull-моделью ADR-014: кнопка одобрения сохранена как «Publish release». Остаются в силе: сторонние actions закреплять по SHA перед продакшном; backup перед миграциями БД; только backward-compatible миграции; авто-откат при провале проверки здоровья.

## ADR-008 · Статусы · proposed
Источник истины — машины состояний ТЗ §8; статусы прототипа — вычисляемое отображение.

## ADR-009 · Типографика и контраст · proposed
Тело 14 px, мета ≥12 px, touch ≥44 px. Вторичные цвета затемняются до AA (проверка в CI). Шрифты self-host (`next/font`): Manrope + Inter (кириллица). Без запросов к Google в рантайме.

## ADR-010 · Безопасность отправки · accepted (ТЗ, CLAUDE)
`send_permission` deny-by-default; согласие адресата ≠ одобрение текста; сервер — единственный арбитр `can_send`; transactional outbox; `unknown_delivery` вместо слепого повтора; `EMERGENCY_STOP_SEND`; отказ → permanent suppression.

## ADR-011 · AI · accepted (ТЗ, CLAUDE)
Режимы: без AI (по умолчанию) → официальный API-ключ → ручной экспорт/импорт. Никакой автоматизации подписок ChatGPT/Claude, cookies и web-login. Контент сайтов/ответов — недоверенный (prompt injection).

## ADR-012 · Бэкапы · proposed
`pg_dump` → `age`-шифрование → VPS-2 → (временно) VPS-3; 7 дневных + 4 недельных; еженедельная проверка восстановления.

## ADR-013 · Клиентское приложение: только Android · accepted (владелец, 2026-11-10)
Контекст: нужно приложение у пользователей, синхронное с сайтом и серверной частью на VPS.
Решение: один веб-клиент (Next.js) — единственный источник интерфейса и логики; Android-приложение (APK) — тонкая оболочка Capacitor, открывающая продакшн-домен `https://ai.vaylonet.ru`. Обновление сайта = обновление функциональности приложения. Оболочка обновляется только при изменении нативной части (иконка, версия, пуши) через релизы GitHub.
Ограничения безопасности: навигация оболочки разрешена только на домен проекта; нативные API для удалённого контента не открываются; cookie HttpOnly/Secure.
Вне объёма: приложение для ПК (отменено владельцем), iOS (отложено; при необходимости — PWA без платного аккаунта Apple).
Предусловия: рабочий backend с настоящей аутентификацией (Фаза 2).

## ADR-014 · Автообновление сервера: pull из ветки main · accepted (владелец, 2026-11-10; заменяет схему с SSH-деплоем и схему с релизами)
Контекст: владелцу сложно настраивать секреты/ключи; из среды разработки недоступен SSH сервера и API секретов GitHub; требование — «вышло обновление на GitHub → сразу на сервере», без кнопки подтверждения на GitHub; одобрение — разрешение владельца разработчику в чате.
Решение: pull-модель. Разработчик заливает изменения в `main` через pull request ТОЛЬКО после явного разрешения владельца. CI (job `test`) гоняет проверки на каждом коммите. На сервере systemd-таймер `lh-update` каждые ~3 минуты читает последний коммит `main` из публичного GitHub API, ждёт успешного job `test` для этого коммита, забирает исходники по SHA, собирает образ локально, запускает, проверяет здоровье, при сбое откатывается; откатанный/провалившийся коммит повторно не разворачивается. Пауза: файл `/opt/leadhunter/.paused`. Секретов, ключей и входящего SSH для деплоя нет.
Риски и меры: любой коммит в `main` с зелёными тестами уходит на сервер → write-доступ только у владельца, рекомендована защита ветки (PR обязателен); деплой привязан к SHA; тесты — обязательное условие; сборка на сервере 4 ГБ ограничена по памяти и использует swap. Репозиторий публичный — в нём не должно быть секретов.
До появления реальной аутентификации (Фаза 2) сайт закрыт временным basic-auth (см. ADR-015: теперь необязательный шлюз).

## ADR-015 · Аутентификация по коду из e-mail, владелец, безопасный отказ без SMTP · accepted (владелец, 2026-11-10)
Контекст: нужна настоящая аутентификация вместо временного basic-auth; секреты нельзя передавать в чат; сервер маленький (1 ядро, 2 ГБ).
Решение: вход и регистрация по одноразовому коду, отправляемому на e-mail (cookie-сессия, ADR-006). `OWNER_EMAIL` — владелец, одобряется автоматически; остальные новые пользователи ждут одобрения владельца в приложении. В prod разрешены `MAIL_BACKEND=http` (основной, см. ниже) и `smtp`; пока почта не настроена, API отвечает 503 `MAIL_UNAVAILABLE` (коды не логируются и не выдаются — «безопасный отказ»). SMTP-параметры и владелец вводятся на сервере командой `lh-config` (скрытый ввод, `.env` 0600, атомарная запись под flock), без передачи секретов в чат. Стек: web + api + postgres + caddy; Caddy проксирует `/api/*` на api, остальное на web; basic-auth остаётся необязательным шлюзом (`BASIC_HASH` непустой / `lh-config gate on`). lh-update собирает два образа, проверяет здоровье обоих и откатывает оба; миграции alembic применяются при старте api и должны быть обратно совместимыми (откат не откатывает схему).
Дополнение (почта через HTTPS-ретранслятор): хостинг VPS (1cent.host) закрывает исходящие порты 25/465/587 (проверено владельцем через /dev/tcp), поэтому коды отправляет `MAIL_BACKEND=http`: api подписывает запрос HMAC-SHA256 и шлёт `{to, code, ttl_minutes}` по HTTPS на PHP-скрипт `infra/mail-relay/lh-mail.php` на хостинге Рег.ру, который сам формирует фиксированное письмо и отправляет его через SMTP ящика `noreply@vaylonet.ru` (локально на хостинге порты открыты). Схема подписи: `HMAC(secret, timestamp.nonce.body)`, допуск ±300 с, одноразовый nonce, тело ≤ 2 КБ, лимиты 5 писем/час на получателя и 300/сутки. Секрет генерирует `lh-config mail-relay` (показывается один раз), пароль ящика вводится только в Shell хостинга. Риски: утечка HMAC-ключа позволяет слать только письма-коды (не произвольный текст) в рамках лимитов — ключ меняется повторным `lh-config mail-relay` + `setup.sh`; доставляемость и лимиты зависят от хостинга Рег.ру (единая точка отказа); пароль ящика лежит в конфиге на хостинге (0600, вне webroot). Прямой SMTP остаётся запасным вариантом.
Последствия: до настройки почты вход невозможен (так задумано); ящик/SPF/DKIM — на стороне Рег.ру (см. OPERATIONS); суммарный потолок памяти контейнеров ~1 ГБ из 1.9 ГБ.

## ADR-016 · Порядок работ: сначала LeadHunter для себя, затем продукт для продажи · accepted (владелец, 2026-11-11)
Контекст: LeadHunter задуман как внутренний инструмент поиска клиентов; продаваемый продукт (AutoFlow или LeadHunter как сервис) — следующий этап.
Решение: сначала завершить MVP LeadHunter для одного владельца (поиск и проверка компаний → оценка → черновики → согласие и согласование → отправка по разрешённым каналам → ответы → CRM). Только после доказанной пользы — лендинг и пилот AutoFlow либо SaaS-вариант (отдельные аккаунты компаний, тарифы, оплата, юридическая проработка).

## ADR-017 · Очередь фоновых задач: в PostgreSQL, без Celery/Redis — пока один сервер · proposed
Контекст: сервер 1 ядро / 1,9 ГБ RAM; Redis и Celery добавили бы ~300–500 МБ и сложность. ТЗ допускает пересмотр, если замер покажет нехватку RAM.
Решение: таблица `jobs` и воркер в процессе API/отдельном контейнере с выборкой `FOR UPDATE SKIP LOCKED`, ограничением параллелизма (1–2), повторами с экспоненциальной задержкой, отменой и возобновлением после рестарта. Интерфейс задач (`enqueue`, `cancel`, состояния) сохраняется, чтобы позже заменить реализацию на Celery при появлении второго сервера.
